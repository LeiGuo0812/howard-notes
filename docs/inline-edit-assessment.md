# 主站登录与原位编辑评估

评估日期：2026-10-01。本次仅评估编辑方式，不实现原位编辑，也不改文章原文或页面设置。

后续已实施主站维护模式，当前使用方式与组件接口见 [主站维护模式](maintenance-mode.md)。下文保留评估时的架构判断。

可以在现有 Quartz + GitHub Pages 架构中实现“登录后留在主站，阅读文章时直接编辑”。建议增加主站的维护模式，复用已有 GitHub 登录、草稿、图片上传与发布能力，不更换托管平台。

## 推荐的使用流程

1. 首页和文章页顶栏提供“登录”。GitHub 授权完成后回到发起登录的页面，阅读位置保留。
2. 所有者登录后，顶栏出现“新建、草稿、页面设置、退出”；文章标题旁出现“编辑”。普通访客继续看到现有阅读页面。
3. 点“编辑”后，就地打开 Markdown 编辑区。桌面并排显示编辑与预览，手机切换“编辑／预览”。格式工具、图片多选上传和粘贴沿用现有能力。
4. 输入时立即更新本机预览；提供“存草稿、发布、取消”。已发布文章存草稿时继续保留访客看到的旧版。
5. 发布后明确区分“已保存至 GitHub”与“已部署上线”。维护者可继续查看自己的最新预览，访客版在部署成功后更新。
6. 草稿箱和页面设置使用主站抽屉或独立面板。无需在每篇文章上摆满全部维护控件。旧后台可在首阶段作为备用入口，之后按使用情况决定是否收起。

## 即时性：编辑预览与公开发布是两件事

现有后台已经有实时预览：`admin/app.mjs` 的正文输入在 160ms 后触发本机渲染。独立后台影响的是“阅读 → 找到文章 → 打开编辑”的操作路径，不是预览必须等服务器。

| 动作                 | 原位编辑后的表现              | 是否需要等待部署                               |
| -------------------- | ----------------------------- | ---------------------------------------------- |
| 修改文字、公式或格式 | 本机预览立即更新              | 否                                             |
| 调整字体、布局和模块 | 维护者本机预览更新            | 否                                             |
| 存草稿               | 保存到 GitHub，已发布原文不变 | 访客版无需更新；现有 main 分支提交仍会触发构建 |
| 发布文章或页面设置   | 写入 GitHub，显示部署状态     | 是                                             |
| 其他访客打开最新版本 | 读取新部署的静态页面          | 是                                             |

当前工作流实际执行依赖安装、测试、类型检查、完整构建、页面验证和 Pages 部署。把编辑器搬到主页面不会绕过这些步骤，因此不能承诺“输入后所有访客同步立即看到”。部署等待应以实际运行状态显示，不写死分钟数。GitHub Pages 支持以 Actions 工作流构建和部署静态站点。[GitHub 官方说明](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages)

## 当前代码能复用的部分

| 模块                                           | 已有能力                                                              | 需要调整的边界                                                                                  |
| ---------------------------------------------- | --------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| `admin/github.mjs`                             | 读取原 Markdown、保存文章、编辑草稿、发布草稿、页面设置、版本冲突检查 | 继续以原文与 SHA 为基线，不从文章 HTML 反推 Markdown                                            |
| `admin/formatting.mjs`                         | 格式工具、撤销重做                                                    | 以编辑器实例绑定控件                                                                            |
| `admin/preview.mjs`                            | Markdown、公式、Mermaid、双链、图片预览及净化                         | 当前双链使用 `../notes/` 相对路径，需要改为注入站点根路径；复杂 Obsidian 嵌入与正式渲染仍需核对 |
| `admin/images.mjs`                             | 图片多选、内容去重、上传到独立仓库                                    | 复用；图片上传即写入图床，取消文章编辑不会删除已上传图片                                        |
| `admin/settings.mjs`、`admin/layout-draft.mjs` | 主题、模块、导航、专题、字体、布局草稿                                | 当前大量依赖固定 DOM ID，需要拆出表单与数据控制器                                               |
| `quartz/components/scripts/layout-preview.ts`  | 已可在浏览器预览页面设计变化                                          | 当前只在后台 iframe 模式启用，可抽出作用于主站的预览函数                                        |
| `admin/auth.mjs`、`auth-service/worker.mjs`    | 所有者 GitHub 登录、仓库写入权限校验                                  | 在移动登录修复后复用，回到原页面；登录状态与文章 DOM 分开管理                                   |

`admin/app.mjs` 目前顶层持有所有表单状态，并直接访问固定 ID。不能把整份脚本加载到文章页就完成集成。需要抽出共享的编辑器、会话和数据服务，后台与主站使用同一组能力，避免两份编辑逻辑逐渐分歧。

## 必须处理的运行边界

**主站内部导航。** Quartz 使用 `micromorph` 替换页面 DOM，导航时运行 `window.addCleanup` 并触发 `nav`。登录会话应保存在独立的内存服务中，控件按页面重新挂载并清理监听。编辑缓冲区不得只存在于将被替换的 DOM 中。导航前先保留草稿，再决定是否离开；仅监听 `prenav` 不能撤销现有导航流程，需要显式的离开保护或导航前检查。

**防丢稿。** 现有文章编辑只有离开确认和显式远端草稿保存，页面布局才有本机草稿。原位编辑应增加文章本机恢复稿，记录文章 ID、原版本 SHA、内容和时间，并在输入后及切后台时保存。手机不应仅依靠 `beforeunload`：移动系统可能直接结束浏览器进程。[MDN 官方说明](https://developer.mozilla.org/en-US/docs/Web/API/Window/beforeunload_event)

**多设备。** 每台设备分别 GitHub 登录。本机恢复稿只属于当前浏览器，点击“存草稿”后才进入 GitHub 并可跨设备继续。保留现有 SHA／目录版本检查：手机与电脑同时编辑同一文章时提示核对，禁止静默覆盖。现阶段不需要增加多人实时协作或 WebSocket。

**登录会话。** 当前短期 GitHub 用户令牌只留在内存，刷新或关页后需要重新登录；网页内的 SPA 导航可以保留。若以后希望刷新、重启后也保持登录，需要单独增加服务端会话、续期和退出能力，不能简单把 GitHub 令牌写进浏览器长期存储。本项目服务端目前不保存刷新令牌。GitHub 默认短期用户令牌为 8 小时；此上限也由本项目回调校验。[GitHub 官方说明](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/refreshing-user-access-tokens)

**权限与内容。** 隐藏编辑按钮只是显示逻辑，实际写入仍须 GitHub 权限和所有者校验。草稿及未发布文章应登录后通过已授权接口加载，不放进公开 HTML、公开搜索索引或匿名预取。当前 `howard-notes` 是公开仓库，草稿和撤下只影响网站展示，仓库原文与 Git 历史仍可访问；原位编辑不会自动让它们变成私人内容。

**原文与本地 Obsidian。** 保存仍写入仓库里的原 Markdown，发布设置继续单独存储。浏览器不能直接修改电脑的 Obsidian 库；已有本机同步脚本比较基线、本地与远端三份文件，在执行同步时才将网页修改带回公开文库。两端同时修改仍按现有冲突处理保留副本。

**普通访客的资源占用。** 登录、编辑器和预览依赖应按需加载。匿名阅读不应加载完整后台、Mermaid 编辑预览和全部原文。登录后也只在打开文章编辑时读取该篇源文件，并按提交版本缓存目录与图片。

## 建议分阶段完成

第一阶段先修好移动登录；再增加顶栏登录、文章旁编辑入口、就地编辑／实时预览、草稿与发布、本机恢复稿和部署状态。保留 Markdown 源文编辑，不直接在已渲染正文上使用 `contenteditable`，以免破坏双链、公式、代码块与原文格式。

第二阶段将新建、草稿箱、图片设置和页面布局搬到主站维护抽屉，共享同一会话。若实际使用证明需要跨刷新保持登录，再独立评估服务端会话；不把这项复杂度强加到第一阶段。

本评估依据当前源码与工作流，没有实施主站编辑改造，也没有对尚未存在的交互宣称浏览器验证通过。
